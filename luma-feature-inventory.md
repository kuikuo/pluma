# Luma feature inventory (for a clean-room P2P rebuild on Pear)

Date: 2026-10-31. Sources: **public documentation only** (help.luma.com, docs.luma.com, public-api.luma.com/openapi.json, public luma.com pages, the luma.com pricing page and the App Store listing). Nothing here comes from a logged-in session or from Luma source code. Descriptions are written in our own words; this inventory describes behaviour, not implementation.

How this was built: five research areas (events, registration, attendee, calendars, platform). A verifier checked each feature against its source. Corrections were applied, features the verifier found missing were added, and cross-area duplicates were merged into one entry under the most relevant area. The verifier marked no whole feature as unsupported. Specific claims inside features that could not be confirmed are listed under [Unverified](#unverified).

**Totals:** 261 features. By area: events 57, registration 55, attendee 57, calendars 52, platform 40. By P2P difficulty: easy 167, needs-seeder 26, needs-server 52, unclear 16. Verification: confirmed 207, corrected 43, added (verifier missed-feature) 11. Buckets: MVP 40, Later 143, Needs infrastructure 78.

Legend: **P2P difficulty**: `easy` means pure Pear (Hypercore/Hyperbee/Autobase/Hyperswarm/Hyperdrive); `needs-seeder` means it works P2P but needs an always-on peer (seeder, indexer or host device) for availability, ordering or key hand-out; `needs-server` means it needs non-P2P infrastructure (email/SMS, payments, OAuth, HTTP gateway, geocoding); `unclear` means the answer is open. Tags after a feature name: *(corrected)* means the verifier amended the description; *(added)* means the verifier found the feature missing from the research.

Machine-readable copy: `luma-features.json` (same entries, plus `verification` and `bucket` fields).

<a id="suggested-buckets"></a>
## Suggested buckets

Rule: **MVP** is the core loop where an organiser creates an event and guests RSVP, check in and get updates, and every MVP item is `easy` in P2P. **Needs infrastructure** is every `needs-seeder` or `needs-server` feature. **Later** is everything else that is easy or unclear but not part of the core loop.

Two things the MVP depends on but cannot get from pure P2P. (1) **Capacity enforcement and waitlist** (needs-seeder) are deferred. In the MVP, the host device is the single approver: use Require Approval, or let the host linearize registrations whenever it is online. (2) **Restricting the venue or link to approved guests** needs key hand-out on approval. The MVP can do this whenever the host is online.

<a id="inferred-data-model"></a>
## Inferred data model

Merged from the public OpenAPI spec and help articles. Field names follow Luma's API where it documents them. The P2P mapping after the model is our suggestion.

**Identifiers.** Luma uses prefixed IDs: `evt-` (event), `cal-` (calendar), `usr-` (user), `gst-` (guest), `g-` (guest check-in key), `ttyp-` (ticket type), plus short ticket keys. Datetimes are ISO 8601 UTC, durations are ISO 8601 (PT2H), timezones are IANA. List endpoints return `{entries, next_cursor}`. `api_id` is deprecated in favour of `id`.

**User / Account.** id, username (3-15 chars, `[A-Za-z0-9_]`), first_name, last_name, display name, avatar (can't be removed once set), bio, socials {instagram, x, youtube, tiktok, linkedin, website}, primary_email, additional_emails[], phone (0..1, unique across accounts), language, theme, optional password, TOTP flag, passkeys[], linked OAuth {google, apple, zoom}, wallets {eth_address, solana_address}, notification_preferences {type -> [email, sms, push]}, blocked_users[], follows (calendar ids), discover subscriptions (city/category), active_sessions[].

**Calendar.** id, name, slug (global namespace shared with event slugs), url, description, avatar_url, cover_image_url, social_image_url, tint_color, is_personal, launch_status {launched, coming-soon, archived}, location {city, region, country, timezone} plus coordinate (or Global), socials, website, event_defaults {visibility, show_guest_list, feedback_email.enabled}. Admin-only settings: submission policy {anyone, admins-only, require-manage-access; accepts external}, event-list visibility {public, member-only}, send limit and unlock state, Plus subscription and seats, Stripe account, payment methods, tax {name, percent}, invoice details {business name, address, memo, sequential counter}, refund policy, Solana treasury wallet, GA/Meta IDs. Equal-rights admins[]. Optionally belongs to an Organization.

**Event.** id, user_id (creator, permanent, receives Contact-Host messages), calendar_id (exactly one managing calendar), name, description_md, cover_url, start_at, end_at, duration_interval (read-only), timezone, url, slug, visibility {public, members-only, private}, location_type {offline, zoom, meet, youtube, twitch, discord, twitter, missing, unknown}, geo_address_json Address, coordinate (coarsened for non-guests when restricted), location_visibility {public, guests-only}, meeting_url (behind per-guest /join redirect), theme, theme style, font, tint_color, display mode, registration_open, max_capacity, spots_remaining (lagging, manage-only), waitlist_status, can_register_for_multiple_tickets, require_approval (derived from ticket types), display_price {amount, currency, is_flexible}, name_requirement {full-name, first-last}, phone_number_requirement, show_guest_list, reminders_disabled, feedback_email {enabled, delay}, confirmation/pending/declined email Markdown, tax_config, FAQs[], tags[], registration_questions[], ticket_types[], hosts[], guest_counts by status, discovery opt-out, featured-in. View vs manage scopes: the view scope hides meeting_url, emails and the precise geo location.

**Address.** address, city, region, country, city_state, full_address, google_maps_place_id, apple_maps_place_id, description (directions), plus a pin override up to 1 km (field name not documented). Input modes: manual, Google place_id, lookup.

**Host (event role).** email, name, avatar, access_level {manager, check-in, none}, is_visible (check-in staff never visible), creator flag. Check-in config: default_scan_mode {standard, express}, lock_scan_mode, per-staff allowed ticket_type_ids.

**TicketType.** id, name (1-30), description (up to 1000), type {free, paid}, cents, currency (lowercase ISO 4217, plus solana_sol and solana_usdc), is_flexible, min_cents, require_approval, is_hidden, valid_start_at, valid_end_at, max_capacity, max_per_guest, tint_color, allowed membership tiers. 1-200 per event; soft-deleted.

**RegistrationQuestion.** id, label, required, question_type {text (multiline), select (options up to 250, multiple), agree-check, company (+job title), phone-number, url, github, instagram, linkedin, telegram, twitter, youtube, terms (text content_md or link url; collect_signature; require_review)}, optional source {calendar question}.

**Coupon.** id, code (1-20, case-insensitive), scope {event, calendar} (an event code shadows a calendar code), discount {percent_off or cents_off + currency}, remaining_count (1000000 means unlimited, 0 means invalidated), valid_start_at/valid_end_at, event_ticket_type_id (if that type is hidden, the coupon is an unlock code). Terms are immutable.

**Guest (per event).** id, user_id, email, name, first/last, approval_status {approved, pending_approval, waitlist, invited, declined, session (meaning undocumented)}, check_in_qr_code (luma.com/check-in/{evt}?pk=g-...), invited_at (null means self-registered), registered_at, joined_at, phone, eth/solana address, registration_answers[], attribution_params {utm_*, gclid, fbclid, wbraid, gbraid, twclid, li_fat_id, ttclid, rdt_cid, yclid}, referrer, event_tickets[], event_ticket_orders[], activity timeline, email delivery log. Display mapping: Going = approved, Pending = pending_approval, Not Going = declined.

**EventTicketOrder / EventTicket.** An order has id, amount, amount_discount, amount_tax, amount_refunded, currency, coupon_info, is_captured, and holds 1..n tickets. A ticket has id, ticket key, event_ticket_type_id, amounts, checked_in_at, is_captured and an invalidation history. Check-in is per ticket. Transfers: from_guest, to_email, tickets[], status {pending, claimed}.

**Blast.** id, event_id, subject (up to 200), content_md, status {scheduled, sent, quarantined}, scheduled_for, sent_at, recipient_groups [{status, event_ticket_type_id?}], recipient_count, email_open_count, sender {user or calendar}, can_edit, can_reschedule. Can be sent until 7 days after the event. System messages: reminders (T-1d, T-1h), feedback, cancellation, update emails.

**Feedback.** guest_id, rating (emoji scale; the latest value wins), text, created_at.

**Calendar listing (CalendarEvent).** calendar_id, event_id or ExternalEvent, platform {luma, external}, status {pending, approved, declined/removed}, access {manage, view}, tags[], submitted_by, removed_by (inferred). ExternalEvent: name, url, start, duration, timezone, address, host string, no cover.

**Tags.** EventTag {id, name, color} (public, per calendar) and ContactTag {id, name, color} (admin-only).

**Contact (calendar person).** id, user_id, email, names, avatar, created_at, source {follow, import, registration}, tags[], event_approved_count, event_checked_in_count, revenue_usd_cents, state {active, unsubscribed, removed, blocked, bounced}, membership {tier_id, status {approved, pending, approved-pending-payment, declined}, registration_answers}.

**MembershipTier.** id, name, description, tint_color, is_hidden, access_info {free, payment-once, payment-recurring (monthly/yearly)} with require_approval, registration_questions[]. One tier per person per calendar.

**Newsletter.** calendar, author, subject, rich body, audience {everyone, tags, tier}, status {draft (private to author), scheduled, sending, sent}, stats {sent, opens, clicks, unsubscribes, skipped}.

**Chat.** Conversation {type: dm, group or event; name; avatar; admins[]; members[] (event chats derive members from approved guests); closed}. Message {author, body, reply_to, reactions, deleted}. Per-user state: archived, muted, read.

**Organization.** id, admins[], calendars[], SSO, CRM connections, org API keys, webhooks.

**Webhook.** id, url, event_types[], status {active, paused}, secret (whsec_), delivery log. Payloads are `{type, data}`.

**Quotas.** Per calendar: weekly send counter (resets Monday 00:00 UTC), sends_unlocked flag, import-limit counter, deliverability metrics. Per key: rate limits.

**Relationships.** User 1..* Calendar (exactly one personal calendar). Calendar *..* admins. Event has 1 managing calendar and *..* listing calendars. Event 1..* Host, 1..200 TicketType, *..* Guest. Guest 1..* Order, and an Order has 1..* Ticket, each referencing a TicketType. Calendar 1..* Contact, and a Contact has 0..1 Membership. Organization 1..* Calendar.

### Suggested P2P mapping
- **Identity:** one keypair per user, with multiple devices paired as writers of a personal Autobase (profile, follows, preferences, local blocklist).
- **Calendar:** an Autobase whose writers are the admins and whose view is a Hyperbee (profile, settings, listings, tags). A personal calendar is a single-writer core. Private admin data (contacts, member tags) lives in a separate encrypted bee shared only by admins.
- **Event:** an Autobase whose writers are the managers (plus check-in staff limited to check-in records), with the event document, ticket types, form schema and hosts in its view. Guests write signed registration, cancel, feedback and join records to their own cores. The host-run indexer linearizes them, and it is the authority for capacity, coupon redemptions and invoice numbers.
- **Confidential fields** (precise address, meeting link, full roster, answers, member-only listings, segment-targeted blasts): encrypt them to approved-guest or tier group keys, and rotate keys when someone is removed.
- **Tickets:** a host-signed payload {ticketId, eventKey, holderPubkey, sig} in the QR code, verified offline by any scanner device.
- **Media:** stored in a Hyperdrive. **Discovery:** Hyperswarm topics per city or category, plus curator-signed index cores served by seeders.
- **Bridges (optional, outside P2P):** email/SMS relay, payment processor, HTTP gateway (embeds, iCal, OG, SEO), OAuth integrations (Zoom, Meet, CRMs), webhook bridge.
